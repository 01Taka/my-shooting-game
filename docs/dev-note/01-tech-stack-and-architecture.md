# 技術スタック選定理由とハイブリッド設計思想

本プロジェクトにおける技術スタックの選定理由と、Canvasゲームエンジン（Phaser）とコンポーネント指向UIフレームワーク（React）を融合させたハイブリッドアーキテクチャの設計思想です。

---

## 1. 技術スタック一覧

- **ゲームエンジン**: Phaser 4 (`phaser: ^4.2.1`)
- **UIフレームワーク**: React 19 (`react: ^19.3.1`)
- **スタイリング**: Tailwind CSS v4 (`@tailwindcss/vite: ^4.3.3`)
- **グローバル状態管理**: Zustand (`zustand: ^5.0.16`)
- **スキーマ検証**: Zod (`zod: ^4.6.7`)
- **ビルドツール**: Vite (`vite: ^8.3.4`)
- **言語**: TypeScript (`typescript: ~6.0.3`)

---

## 2. なぜ Phaser 4 × React 19 のハイブリッド構成なのか？

### 思考フレームワーク：Canvas vs DOM の二元論を超えた「適材適所」

Webでゲームを作る際、よく「全画面Canvasのみで作るか」「HTML/CSSのDOMのみで作るか」という二者択一で議論されますが、両者には明確な得手不得手があります。

| レイヤー                                                                     | 最適な技術                       | 理由・特性                                                                                     |
| :--------------------------------------------------------------------------- | :------------------------------- | :--------------------------------------------------------------------------------------------- |
| **ゲームプレイ領域**<br>（キャラ移動、弾の軌跡、当たり判定、物理演算）       | **Phaser 4**<br>(WebGL Canvas)   | 60FPS固定のゲームループ、WebGLによる大量スプライトの超高速描画、Arcade物理演算、テクスチャ管理 |
| **アプリケーションUI領域**<br>（設定画面、全画面切替、フォーム、スライダー） | **React 19**<br>(DOM / Tailwind) | ネイティブフォーム部品、アクセシビリティ、CSSトランジション、レスポンシブ配置、開発速度        |

### なぜゲームUIすべてを Phaser で自作しないのか？

Phaser の Canvas 内で矩形やテキストを組み合わせてスライダーやトグルスイッチ、モーダルを自作することは可能ですが、以下の大きなデメリットがあります：

1. **車輪の再発明**: フォーカス管理、アクセシビリティ、スライダードラッグの慣性計算などをすべて手書きする必要がある。
2. **デザイン改修のコスト**: CSSならクラス名を1つ変えるだけの調整が、Canvasコードの座標再計算・描画命令の書き直しになる。
3. **文字品質の限界**: Canvasでラスタライズされた文字よりも、OS標準のネイティブフォントラスタライザを通る DOM テキストの方が圧倒的に美しい。

このため、**「ゲームワールドは Phaser に任せ、設定モーダルやHUDの一部は React に任せる」** という責務分離を採用しました。

## 3. なぜグローバル状態管理に Zustand を採用したのか？

### React Context の限界

React Context は React コンポーネントツリーの内部でしか使用できません。  
しかし、本ゲームでは **「Phaser の Scene コールバック内から直接設定を開きたい」「ゲームのスコアをReact側に伝えたい」** という双方向の通信が発生します。

### Zustand の採用理由

1. **React 外からの直接アクセス**:  
   React のフックを使えない Phaser のメソッド内からでも、`useGameSettings.getState().openSettings()` で直接ステートを変更できます。
2. **EventBus との共存**:  
   軽量な通知には `EventBus` を使い、永続化やReactコンポーネントと同期するステートには `Zustand` を使うという明確な使い分けが可能です。
3. **ゼロボイラープレート**:  
   Redux のような複雑な設定や Provider によるラップが不要で、小〜中規模ゲームに最も適しています。
