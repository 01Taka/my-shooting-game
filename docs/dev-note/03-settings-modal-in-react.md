# なぜ設定画面を Phaser ではなく React で構築したのか

本ゲームでは、当初 Phaser のシーンとして作成されていた `SettingsScene` を完全に削除し、React コンポーネント（`SettingsModal`）に移行しました。その意思決定プロセスと UI デザインの思想です。

---

## 1. 意思決定の背景（なぜ Phaser シーンをやめたのか）

### Phaser で UI を作ることの限界

1. **スライダー操作の自然さ**:
   音量スライダー（`<input type="range">`）は、ブラウザネイティブのものが最も慣性・タッチ精度・キーボード操作（矢印キー操作）に優れています。Phaser 内で線を描いてドラッグ座標を計算する自作スライダーは、タップ検出のズレやバグが発生しやすい課題がありました。
2. **フルスクリーン・横画面固定 API の呼び出し**:
   フルスクリーン切り替えはブラウザの DOM API です。React のボタンコンポーネント内に置く方がコードの見通しが良く、状態管理（Fullscreen中かどうか）の同期も簡単です。
3. **アイコン表現のクオリティ**:
   Lucide React のベクターSVGアイコン（音量ON/OFF、全画面化、閉じる「×」）をそのまま使えるため、Canvas で自作するよりも圧倒的に美しいデザインが得られます。

---

## 2. ゲーム画面上の UI 整理思想

リファクタリング前は、ゲーム画面の上に以下の UI が常時浮いていました：

- 左上: `「状態: 準備完了 / プレイ中」`
- 右上: `「全画面」切り替えボタン`

### 思考フレームワーク：ゲーム画面のノイズ削減

スマホ横画面は画面領域（縦幅）が限られています。  
ゲームプレイ中に「状態」ピルを見る必要はなく、また右上の「全画面」ボタンもゲーム中に何度も押すものではありません。ゲーム中に誤タップするリスクすらありました。

### 採用したレイアウト構成

- **左上の状態ピルを削除**: ゲーム世界に没入できるよう、不要なデバッグ用UIを完全排除。
- **右上の全画面ピルを設定画面内へ移動**: 全画面化は「設定」の一部としてモーダル内に集約。
- **結果**: ゲームプレイ中は **「ゲーム画面 ＋ 左下の十字キー ＋ 右下のショットボタン」** だけが配置された、アーケードゲーム機のような極めてクリーンな画面を実現しました。
